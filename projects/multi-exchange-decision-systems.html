System framing

A dependable trading system is a chain of checked decisions.

I worked on a multi-exchange platform where data quality, time alignment, research controls, order state, and operational records all need to agree. The engineering work is not only the model or strategy; it is the interface between each system boundary.

This page explains the end-to-end implementation pattern at an architectural level. It intentionally omits proprietary source code, credentials, deployment configuration, live strategy parameters, and performance claims.

Scope and disclaimer. This is a professional engineering overview, not trading advice or a recommendation to use any strategy, exchange, or financial product. Descriptions are evidence-led and distinguish the platform architecture from investment outcomes.

System route

How the platform moves from raw information to an auditable action.

Each stage has an explicit input, a practical transformation, and a record that lets the next stage be checked.

01 / DATA

Connect, normalize, and store market history.

Exchange and broker APIs provide OHLCV and account-facing data. The ingestion layer organizes it by venue and instrument, then writes it into PostgreSQL / TimescaleDB tables designed for time-series access.

Implementation focus: API adapters, symbol mapping, timestamp normalization, incremental pulls, table design, and repeatable storage jobs.
02 / PREPARE

Turn stored candles into research-ready inputs.

Scheduled workflows resample multiple timeframes, prepare features, and assemble market-regime context. A central concern is keeping time windows aligned so a research signal cannot see data that would not have existed at the decision point.

Control points: timezone handling, pandas index integrity, resampling boundaries, missing bars, and look-ahead-bias checks.
03 / RESEARCH

Compare models and strategies through a repeatable process.

A model registry supports experiments across scikit-learn, XGBoost, LightGBM, and CatBoost. Optuna coordinates hyperparameter search, while strategy configuration and backtesting provide a consistent way to compare candidate ideas against historical data.

Evidence trail: experiment inputs, configuration choices, generated strategy variants, run logs, and tracked evaluation context.
04 / DECIDE

Apply rules that convert a research result into a controlled signal.

Signal generation combines the configured strategy logic with timing, symbol, and regime context. Before the execution layer receives anything, the system must make it clear which instrument, direction, timeframe, and state the signal represents.

Engineering concern: avoid duplicate or stale signals, retain source context, and keep simulator and ledger state comparable.
05 / EXECUTE

Translate an approved intent into venue-specific order operations.

Per-exchange executors manage the differences among Binance, Bybit, OKX, Kraken Futures, Hyperliquid, and MetaTrader 5 integrations. The practical work includes placement, trailing-stop behavior, TP/SL reconciliation, duplicate-order handling, and recovery from partial or delayed state.

Operational reality: exchange responses, order identifiers, changing fill state, and platform-specific error paths all need explicit handling.
06 / RECONCILE

Compare what was intended, sent, and actually recorded.

Execution results return to ledger and signal records so mismatches can be investigated. Reconciliation protects against drift between strategy state, exchange state, and the internal record used by simulation or monitoring.

Checks include: missing signals, duplicated orders, TP/SL state, strategy-to-ledger drift, and synchronization recovery.
07 / OBSERVE

Expose the system through logs, schedules, and interfaces.

MLflow experiment tracking, cron-scheduled tasks, VPS operations, and a React dashboard provide visibility into research and operational workflows. The dashboard is a surface for strategy, market-regime, and PnL-oriented views rather than a substitute for the underlying records.

Delivery focus: run logs, task scheduling, API connections, database health, and React-facing monitoring surfaces.

Implementation detail

What the end-to-end work looks like in practice.

These areas summarize responsibilities and technical decisions that can be discussed openly without exposing the platform’s private implementation.

01 / Data infrastructure

Time-series data with operational discipline.

PostgreSQL and TimescaleDB support market-data storage, signal records, and ledger-oriented workflows. I worked on schema-level concerns, data migration from a Windows workstation to an Ubuntu VPS, backup automation, authentication troubleshooting, and scheduled data jobs.

  • OHLCV storage organized for repeated time-series queries.
  • Multi-timeframe resampling and regime-processing workflows.
  • Backup, migration, and server-side diagnosis across local and VPS environments.

02 / Research & optimisation

Experiment without losing the decision trail.

Instead of treating a model as a one-off artifact, the workflow keeps configuration, search context, and backtest output connected. The registry covers tree-based ML models, with Optuna used for optimisation and MLflow used to retain experiment context against a PostgreSQL backend.

  • scikit-learn, XGBoost, LightGBM, and CatBoost model registry work.
  • Optuna-based parameter search, including distributed trial allocation.
  • Backtesting and regime-aware investigation before execution integration.

03 / Execution engineering

Design for the exchange that actually responds.

Live-facing execution requires adapter-level handling rather than assuming every broker exposes the same order semantics. My work included diagnosing trailing stops, take-profit/stop-loss mismatches, linked-order identifiers, and execution records that no longer matched the simulator or ledger.

  • Venue-aware order workflows across six exchange and broker integrations.
  • Duplicate-order safeguards and signal-to-ledger synchronization work.
  • Practical debugging from API response through internal execution state.

04 / Operations & interface

Keep the system inspectable after it ships.

Automation and visibility are part of the implementation. I worked with Git-based branches and review practices, cron-scheduled jobs, log-based debugging, and React-facing dashboards for strategy, PnL, and market-regime views.

  • Linux/VPS task scheduling and server-side investigation.
  • MLflow, database records, and logs as operational evidence.
  • React dashboard delivery and API/CORS troubleshooting.

Failure modes

The work that protects the workflow is often invisible.

The platform became more dependable through targeted diagnosis of problems at the edges between components.

01

Time alignment

Resolved recurring timezone and DatetimeIndex issues across pandas resampling and multi-timeframe paths, with particular attention to data availability at signal time.

02

State drift

Investigated missing signals, ledger recovery, and gaps between simulator assumptions, execution records, and current exchange state.

03

Execution mismatch

Diagnosed trailing-stop behavior, TP/SL reconciliation, exchange-specific response differences, and duplicate linked-order scenarios.

What this record does not claim. It does not present proprietary strategy rules, live account counts, capital allocation, backtest returns, latency results, or model-performance percentages. The value of this record is the implementation method: make each handoff inspectable, repeatable, and recoverable.
